# 検証環境： エージェントが自分で画面を確認できる仕組み

## 問題
- Muse の VM には /dev/kvm が無く、ハードウェア加速の Android エミュレータが動かない
- そのため cc / cx / Muse の誰もアプリの画面を自分で見られない。視覚確認はすべてユーザーの実機スクショ経由で、遅く、スクロールの滑らかさ（QC-06）のような「動き」の判定は静止画では原理的にできない

## 目的
変更のたびに、エージェントが人の手を借りずに「起動する・画面が崩れていない・色とレイアウトが仕様どおり」を証拠（スクショ）つきで確認できる状態にする。実機の触感と本人の実データでの確認は引き続きユーザーの実機が担う（役割分担は §制約）。

## 案の比較
### 案A: ユーザー PC 上のエミュレータを遠隔操作
- PC（Ryzen 7 7730U / 16GB、Windows）に Android エミュレータを置き、PC 側 Claude Code が起動・撮影し、結果を VM 側と共有する（Tailscale 経由の ADB 接続も候補）
- 長所: 実機に近い速度と描画。短所: PC の電源・常駐が前提、初期設定の手間が一番大きい

### 案B: VM 上でソフトウェア描画エミュレータ
- KVM なしの純エミュレーション。VM の規模（1.5 vCPU / 6GB）では起動・操作ともに極端に遅い見込み
- 採否は時間枠を切った実験で決めるが、本命にしない

### 案C: CI（GitHub Actions）でエミュレータを回す
- GitHub の Ubuntu ランナーは KVM が使えるため、android-emulator-runner で実エミュレータが動く。公開リポジトリなので追加費用なし
- 撮影だけでなく**実際の操作**も行う： Compose UI Test / Espresso のシナリオテスト（タブ切替、日タップでポップアップ表示、スクロール、ボタンの存在確認など）と adb の input 操作でアプリを本当に動かし、各ステップのスクショと画面構造（uiautomator dump）を成果物として返す
- 短所: 操作は「シナリオを書いて実行させる」バッチ型で、画面を見ながら次の一手を決める対話的な操作はできない（1回の実行に分単位かかる）

### 案D: エミュレータなしの JVM スクショテスト（Roborazzi 等）
- Compose の画面を JVM 上で描画して PNG 化し、単体テストとして check.sh / CI に組み込む
- 長所: 一番安く速く、既存の gate にそのまま乗る。色・レイアウト・文字の収まりの回帰検出に強い
- 短所: 実 GPU 描画でも実機でもないため、スクロールの触感や実フォント描画の最終確認にはならない

## 推奨（段階構成）
1. **Phase 1（先行）: 案D** — 主要画面（月表示・未ログイン案内・日ポップアップ）のスクショテストを導入し、変更のたびに after スクショが自動で残る状態にする。これは描画確認専用で、操作のテストではない
2. **Phase 2: 案C** — 実エミュレータでの起動確認に加え、シナリオテストによる実際の操作（タップ・切替・スクロール）とステップごとの撮影を workflow_dispatch（手動実行）で用意し、「動き」の確認をユーザーの実機なしで一次判定できるようにする
3. **Phase 3（必要になったら）: 案A** — PC エミュレータでの対話的操作。エージェントが画面を見ながらその場で操作を決める形は、この構成でのみ可能。Phase 1/2 で不足を感じた場合に検討する

## 制約・役割分担（変わらないこと）
- 本人の Google アカウントでエミュレータにサインインしない。エミュレータ側はテスト用の画面状態（未ログイン／ダミーデータ）で確認する
- 実機の触感（スクロールの滑らかさ等）と実データ表示の最終判定は、引き続きユーザーの実機＋本人の目
- 公開リポジトリの原則10に従い、CI の権限拡大や新しい外部サービス接続は Muse が確認してユーザーに報告してから行う

## Phase 2 の弱点と、その解決策（2026-11-21 ユーザー指摘を受けて追記）
Phase 2（CI エミュレータ）の弱点は「操作がバッチ型で対話的でない／1回に分単位かかる」こと。これへの解決策として、Phase 3 を次の構成に具体化する：

- **PC 常駐エミュレータ＋ADB over Tailscale**: ユーザー PC 上でエミュレータを起動しておき、VM のエージェント（Muse / cc / cx）が Tailscale 経由で ADB 接続し、screencap と画面構造を見ながら tap / swipe / keyevent をその場で判断して操作する。バッチではなく対話型の操作が VM 側から可能になる
- **操作レイヤーは mobile-mcp を使う**（2026-11-21 GitHub 調査）: `mobile-next/mobile-mcp`（★10.7k）が本命。エミュレータ/実機を ADB 経由で操作する MCP サーバーで、画面構造（アクセシビリティツリー）とスクショを返し、要素単位のタップ・スワイプ・文字入力・アプリ起動ができる。手書き ADB スクリプトよりエージェントとの相性が良い。代替候補: `software-mansion/argent`（★3.2k）。注意点: これらは「操作レイヤー」であって、エミュレータを動かすホスト自体は別途必要（PC か CI）。VM の KVM なし問題はこれでは解けない
- 前提: PC の電源が入っていてエミュレータが起動していること（必要なときだけ起動する運用でも可）。ADB 接続は Tailscale のプライベートネットワーク内に閉じ、公開はしない
- それでも残る制約（正直な線引き）: 実機そのものではないので、実機のタッチ感・実アカウントでのサインイン確認は引き続きユーザーの実機が担う。操作1回ごとに秒単位の遅延はある（映像ストリームではない）

## 決定（2026-11-21 ユーザー）
- Phase 1・Phase 2 を実施する（CI ジョブ追加も承認）。弱点は上記の Phase 3 構成で解決を図る
