# v2 提案: 書き込み対応（作成・編集・削除）

起案: 2026-11-22、Muse（ユーザーの「V2最後までgo」を受けて）。v1（読み取り専用）は同日完了し、本提案が v2 の正本の入口になる。

## 目的
MuseCal から予定の作成・編集・削除までできるようにし、予定管理がこのアプリで完結する状態にする。v1 のままでは「見るだけ」で、登録は別アプリや Web が必要だった。

## スコープの判断（この提案に含まれる決定）
1. **権限は `calendar.events` ＋ `calendar.calendarlist.readonly` へ拡張する**（現行 `calendar.readonly` から）。予定の読み書き＋カレンダー一覧の読み取りだけが対象で、カレンダーの共有設定変更やカレンダー自体の削除はできない最小権限の形。当初は `calendar.events` 単独の想定だったが、calendarList.list は `calendar.events` では認可されない（Google 公式ドキュメント。V2-1 実装時に Codex が発見）ため、一覧読み取り用のスコープを併せる形に訂正した（2026-11-22）。Google Cloud の同意画面へのスコープ追加（Muse がブラウザで実施）と、端末での再同意が必要になる。
2. **操作は作成・編集・削除**。編集項目はタイトル、日時（開始・終了）、終日切替、所属カレンダー、色（標準11色＋色なし）、**場所、説明**（2026-11-22 ユーザー追加指示。当初は非対象だったが、予定の「内容」が現状アプリで表示もされないため、表示と編集の両方を v2 に含める）。参加者・通知は v2 の非対象（必要なら後続で別途提案）。
8. **カレンダー表示の選択を固定する**（2026-11-22 ユーザー追加指示）: 下部のタブで表示 ON/OFF した選択を端末に保存し、次回起動時も前回の選択のままにする（選択したカレンダーの予定だけが表示される）。
3. **繰り返し予定**の編集・削除は「この予定のみ」「すべての予定」を選べる形を目標にする。実装上の制約が出たら V2-3/V2-4 で切り分けて記録し、単体予定の完成を優先する。
4. **入口**: 月表示に新規作成ボタン、日ポップアップ／予定タップから編集画面へ。
5. **オフライン書き込みは入れない**。書き込みはオンライン必須とし、失敗時は V1-5 と同じ日本語の理由＋再試行で示す（キューイングはしない）。
6. **書き込み後は該当窓を再取得**して表示とキャッシュをサーバーと一致させる。楽観表示（先に画面だけ変える）はしない。
7. 色の自動付与はしない（ユーザーの色付けルールは手動選択に委ねる）。

## リスクと対処
- スコープ変更直後は、再同意が済むまで読み取りも 401/403 になり得る。V1-5 の許可系エラー文言（「読み取りの許可を確認できませんでした…ログインし直してください」）で案内される既存の流れを維持し、V2-1 で再同意フローを最初に固める。
- 誤削除の対処として、削除は確認ダイアログ必須。取り消し（ゴミ箱からの復元）は API の範囲外なので入れない。

## 進め方
tasks.md の V2-1〜V2-5。検証は EM-3 のフロー（エージェント一次判定→ユーザーは最終判定のみ）。書き込みの実機確認（Web 側との一致）は QC-12 として V2-5 で記録する。
