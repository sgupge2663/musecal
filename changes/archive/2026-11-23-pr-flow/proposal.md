# 提案: 統合を PR 検問型へ移行する（2026-11-23、ユーザー指示）

## 背景と目的
現行の統合は「ブランチ CI の成功を Muse が確認してからローカルで merge」する手順依存で、憲法9条（強制は文章でなく仕組みで）に対して統合ゲートだけが仕組み化から漏れている。ユーザーの指摘（2026-11-23: PR による機械的な検査ゲートが必要ではないか）を受け、統合を GitHub の PR＋必須チェックに移し、赤い変更が物理的に main へ入らない形にする。あわせて、2026年現在の AI 駆動開発の本流（タスク→PR が基本形）にも揃える。

## 決定事項
1. **main への統合は PR 経由のみ**。ルールセットで「PR 必須＋必須ステータスチェック（Build APK の build ジョブ）＋force push 禁止」を有効化し、**バイパスアクターは置かない**。
2. **記録はブランチに相乗りする**。レビュー記録とタスクのチェック付けは、統合後の main への直接コミットではなく、マージ前の作業ブランチ側へコミットする。STATUS 等の横断記録も次の作業ブランチに相乗りする。これにより統合後の直接 push 自体が不要になる。
3. **マージ方式は merge commit のみ**（リポジトリ設定で squash / rebase を無効化）。従来どおり prune が統合済みを判定できる形を保つ。マージ後にリモートブランチは GitHub の自動削除で消す。
4. **レビューの置き場所は PR と work/ の二重**とする。レビュア役エージェントは PR にレビューコメントを投稿し、従来の work/ レビュー記録もブランチ側コミットで残す。なお単一アカウント運用のため GitHub の正式な Approve は使えない（自分の PR は承認できない仕様）。機械化の範囲は「PR 経由必須＋CI 緑必須」までで、レビュー実施の担保は従来どおり著者≠検査役の運用が担う。
5. **「ブランチを main に最新化してから」は必須にしない**（ルールセットの up-to-date 要求はオフ）。並行する PR 同士をマージ順に処理できる形を保ち、コンフリクトは後続 PR 側で解消する。

## 移行の順序（鶏卵問題の回避）
ルールセットを有効化した瞬間から直接 push ができなくなるため、順序を固定する: (1) 本提案とタスクを main へ直接コミット（移行前の最後の直接 push として記録する）。(2) PRF-2/PRF-3 を作業ブランチで実装し push する（ブランチへの push は従来どおり可能）。(3) レビューと記録相乗りコミットまで終える。(4) GitHub 設定とルールセットを有効化する。(5) そのブランチを PR 化し、新フローで統合して実証とする（PRF-4）。(6) 直接 push が拒否されることを負の対照で確認する。

## 影響
- AGENTS.md「ブランチ運用」の統合手順が PR 前提に変わる。
- scripts/branch_ops.sh は、リモートブランチが GitHub に消されている状態へ追随する（prune のリモート削除は「既に無い」を正常として扱う）。audit の判定は不変。
- 統合ごとにかかる時間は数分増える（PR 作成・CI・レビュー投稿・サーバー側マージ）。
